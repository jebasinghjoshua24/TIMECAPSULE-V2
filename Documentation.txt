2. Fragment Method – A Universal Learning Framework
Status: ✅ Designed, tested on self, documented
Domain‑independent: Works for coding, biology, physics, languages

Core Principle
Knowledge is nested fragments (like atoms). Learn by recognizing patterns across fragments, not memorizing isolated facts.

The 7‑Step Process
Step	Action	Example (JavaScript .map())
1	Keyword + syntax	.map(callback) transforms array elements
2       Example for what input is given for what output          .map(array) -> array 
3	Input / output only	Input [1,2,3] → output [2,4,6]
4	Learner finds logic	Writes own implementation
5	Compare with optimal	Sees why native method is better
6	Understand why	Discovers underlying principle (immutability, efficiency)
7	Debug combined concepts	Fixes broken code mixing map, filter, reduce
Why It Works
Active construction – not passive reading

Pattern recognition – transferable across domains

Error‑driven – mistakes become learning opportunities

AI‑compatible – instant validation, infinite practice problems

Claim
A programmer who knows one language (e.g., Python) can learn another (e.g., Java) in 2 weeks using the Fragment Method.

  Consequence if left: Server starts but users table never created. Every signup/login returns "no such table" error. Whole app broken silently.

  Consequence if left: Same as above — the entire db.exec() fails, NO tables are created at all.

• Fix: Proofread SQL carefully, matching quotes and parentheses

Signup Route:
• Error: Wrote bcrypt(hashSync(password, 10)) instead of bcrypt.hashSync(password, 10)
  Consequence if left: Node crashes on signup — "hashSync is not defined". Every signup attempt fails. Users cannot register.
• Fix: Used dot notation (bcrypt.hashSync) — the method belongs to the bcrypt object

Learned: bcrypt is a one-way hash designed for passwords. The 10 is cost factor (higher = slower = harder to crack).

Login Route:
• Added ban check before returning JWT token — banned users get 403 even with valid password
  Consequence if left: Banned users log in normally, then wonder why they can't view capsules. No feedback given about ban status.
• Learned: JWT is stateless auth. Token carries { id, username, isAdmin }. Server never stores sessions.

HTTP Status Codes:
• 400 = bad request (missing fields)
• 401 = authentication failed (wrong password)
• 403 = forbidden (banned, not admin)
• 404 = not found
• 409 = conflict (duplicate username)
• 201 = created successfully

Route Path Bug:
• Error: Wrote app.post('api/ban') without leading /
  Consequence if left: Browser sends POST to /api/api/ban or api/ban (depends on page). Server never responds. Admin thinks ban is broken. 403 "Admin access required" is never reached.
• Fix: Every route must start with / like '/api/ban'
• This pattern repeated across 3 different routes before I internalized it

Capsule CRUD:
• Error: Used .get() instead of .all() on search
  Consequence if left: Only 1 user ever appears in search results — the first match alphabetically. Users think the app is broken when their friend doesn't show up.
• Fix: .all() returns all matching rows, .get() returns first row only
• Error: Wrote db.prepare().add()
  Consequence if left: Node crashes with "add is not a function". Capsules page loads nothing.
• Error: Used .run(capsule) passing whole object instead of .run(req.params.id)
  Consequence if left: SQLite tries to insert the word "[object Object]" into the WHERE clause. Query either fails or deletes nothing. Capsule never gets deleted.
• Error: UPDATE capsules SET isArchived = ? without WHERE clause
  Consequence if left: Every capsule in the database gets archived/unarchived at once. User opens their capsule list and sees 0 capsules (all archived) or all unarchived. Mass data corruption.
• Fix: Always include WHERE id = ? on UPDATE/DELETE

Column Placement Bug:
• Error: Added isArchived, isFavorite, isPinned columns inside the bans table by mistake
  Consequence if left: Capsules table never gets these columns. Creating a capsule with isArchived: 1 still saves it as readable. The archive/favorite/pin APIs all fail with "no such column" because the UPDATE is targeting the wrong table.
• Fix: Moved them to the capsules CREATE TABLE where they belonged

Variable Name Bugs:
• Error: Destructured userID (capital D) but used userId (lowercase d) later
  Consequence if left: userId is undefined, so the if(!userId) check always triggers. Route always returns 400 "userId is required". Ban route never works. Admin thinks bans are broken.
• Error: Wrote capsule.isArchived as capsules.isArchived (plural)
  Consequence if left: "Cannot read property isArchived of undefined" — crash on archive. Every archive attempt fails.
• Error: Wrote DELETE FROM bands instead of bans
  Consequence if left: "no such table: bands" — unban returns 500 error. Admins cannot unban users.
• Fix: Consistent naming — userId everywhere, singular capsule, double-check table names

Edit Route:
• Error: Destructured req.params.id as const { capsule }
  Consequence if left: capsule is undefined. The if(!capsule) check triggers. Route always returns 404 "Capsule not found" even if it exists. No capsule can ever be edited.
• Fix: const capsuleId = req.params.id or just use req.params.id directly
• Error: Used 401 for missing title → should be 400
  Consequence if left: Frontend receives 401, interprets it as "you need to log in" and redirects to login page. User loses their form data. Very confusing UX.
• Fix: 400 = client sent bad data, 401 = not logged in

Frontend Integration:
• Created api.js helper to centralize Authorization header + JSON handling
• Updated handleSignUp and handleLogin to call API via fetch() instead of localStorage
• Updated initializeCapsules() to fetch capsules from server on page load (added async)
• handleCreateCapsule: initially forgot to mark function async
  Consequence if left: "await is only valid in async function" — SyntaxError at runtime. Capsule creation never works. Button click does nothing (no error shown to user if uncaught).
• Learned: All functions using await must be declared async.
• Also: api.post without await starts the request but doesn't wait for the response. Capsule shows in the list 0.5s later (when the response finally arrives and renderAll fires) or never. Creates race conditions.

Query Parameters:
• /api/users/search?q=jebas — the ?q= part is a query parameter
• req.query.q reads it from the URL
• SQL LIKE '%jebas%' matches usernames containing "jebas" anywhere
• % are SQL wildcards

Key Security Concepts Learned:
• SQL injection: ? placeholders in prepared statements prevent it — values are treated as data, never SQL code
• bcrypt: adaptive hashing — slow by design, automatic salting
• JWT expiry: tokens expire in 7 days, limited window if stolen
• Generic error messages: Same "Invalid username or password" for both wrong user and wrong pass — prevents username enumeration
• Never send password hash to client
• .env file: secrets stored outside code, .gitignore prevents commits

Friend API Routes (complete):

Accept Route (/api/friends/accept):
• Takes sender's userId from req.body
• Finds pending row WHERE userId1 = sender AND userId2 = current user
• Updates status to 'accepted'
• Error: Wrote route that created a new row instead of updating the pending one — would create duplicate relationships
  Consequence if left: Two rows for the same friendship (one 'pending', one 'accepted'). Confuses the list query. Duplicates everywhere.

• Error: Checked both directions in UPDATE but only one direction had the pending status — OR without parentheses mangled SQL logic
• Error: if(existing) returned "No pending request" — logic inverted, should be if(!existing)
• Fix: SELECT the pending request first, capture its id, UPDATE WHERE id = ?
• Learned: A friend request system is two-step — INSERT a pending row, then UPDATE it on accept. Don't INSERT a second row.

Decline Route (/api/friends/decline):
• Same validation as accept but DELETEs the pending row instead of updating
• Error: SQL had double WHERE clause (WHERE WHERE) — DELETE syntax error
  Consequence if left: "SQLITE_ERROR: near WHERE" — 500 error on every decline. No request can be declined.
• Error: Message said "accepted" instead of "declined" — copy-paste leftover
• Fix: Single WHERE, corrected messages

Remove Friend Route (/api/friends/remove):
• Takes friend's userId from body, deletes approved row between both users
• Error: Used accepted as unquoted variable instead of string 'accepted' — ReferenceError
  Consequence if left: "accepted is not defined" — server crashes on every remove. Nobody can unfriend anyone.
• Error: Operator precedence — AND bound tighter than OR, so status filter only applied to second half of OR pair
  Consequence if left: Pending requests could be deleted. Users could silently cancel incoming requests without accepting first.
• Error: DELETE ... WHERE id = ? OR id = ? with userId as second value — userId is not a row id
  Consequence if left: Tries to delete a row whose primary key matches a user ID. Either no row deleted (silent fail) or wrong row deleted.
• Fix: Proper parentheses ((A OR B) AND status), string 'accepted', delete by existing.id only

Learned: AND binds tighter than OR in SQL. Always parenthesize OR pairs: ((cond1 OR cond2) AND cond3).

Friend List Route (/api/friends/list):
• GET route, finds all approved rows where current user is userId1 or userId2
• Maps over rows, finds the friend's ID (the one that isn't the current user), looks up their username/avatar
• Returns { friends: [ { id, username, avatar, since }, ... ] }
• Error: Used WHERE id = ? — id is the row's primary key, not a user column
  Consequence if left: Looking for a row whose row number matches a user ID string. Never matches. Always returns empty list.
• Error: Used .get() instead of .all() — returns only 1 friend
• Error: Mapped over undefined friends variable instead of query result
  Consequence if left: "Cannot read property map of undefined" — crash on page load.
• Fix: Two-step — query rows with .all(), then .map() over the rows array

Learned: Friends list needs a JOIN-like reshape — raw rows have userId1/userId2, but the frontend needs { username, avatar, since }. The ternary (f.userId1 === me ? f.userId2 : f.userId1) picks the friend's ID.

Concepts Reinforced:
• UPDATE existing rows instead of INSERT for accept/decline workflows
• .get() vs .all() — singular vs plural results
• SQL operator precedence — ((A OR B) AND C) not (A OR B AND C)
• Reshaping DB rows before sending to frontend — raw data ≠ API response

Task Class:
• Fields: id (int), title (String), priority (int), deadline (String), isCompleted (boolean)
• Constructor using setters
• Getters and setters for all fields

ArrayList (Resizable Array):
• ArrayList<Task> tasks = new ArrayList<>() — dynamic list that grows as tasks are added
• add(task) — appends to end
• get(index) — retrieves by position
• remove(index) or remove(object) — deletes
• size() — returns count
• Error: Tried to remove by task ID as if IDs were ArrayList indices
  Consequence if left: ArrayList indices start at 0, task IDs start at 1. tasks.remove(3) would try index 3 on a 3-element list (indices 0,1,2) — crashes with IndexOutOfBoundsException.
• Fix: Loop through list, compare task.id field, then remove the matched object, not the index.

Linear Search Algorithm:
• Loop through ArrayList, check each task's .id field until match found
• O(n) time — worst case checks every element
• Used for: delete by ID, mark complete by ID

For-Each Loop Bug:
• Used for(Task task: tasks) loop and called tasks.remove(task) inside it
  Consequence if left: ConcurrentModificationException — Java forbids modifying a list while iterating over it with for-each. Program crashes on every delete.
• Fix: Switched to regular for(int i = 0; i < tasks.size(); i++) loop, then break after remove.

Reference vs Value:
• Task task = tasks.get(i) returns a reference to the actual object in the list
• task.setIsCompleted(true) modifies the task directly — no need to "put it back" with tasks.set()
• Error: Wrote tasks.set(loop, task) after modifying — redundant, object already updated

Concepts Learned:
• Classes/objects — constructor, fields, methods
• ArrayList — dynamic array vs static array (fixed size, can't grow)
• Linear search — simplest search algorithm
• For-each vs indexed for loop — for-each is read-only, can't modify list
• References — objects in Java are references, not copies
• Scanner — handling nextInt() vs nextLine() quirks
